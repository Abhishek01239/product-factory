Supabase · Oct 30, 2026

Your next Supabase table will throw 42501. Find out which ones, and fix them without GRANT ALL.

On October 30 Supabase stops giving new public tables to the Data API automatically. A table without a GRANT fails with "permission denied for table" for supabase-js, REST and GraphQL, even with the service_role key. This check reads your migrations, your RLS policies and your supabase.from() calls, and writes the grants each table actually needs.

The timeline

  1. May 30, 2026New projects stop auto-granting new tables to anon, authenticated and service_role.
  2. Oct 30, 2026Same default for every existing project. Existing tables keep their grants; new ones get none.
  3. After thatEvery create table needs its own grant, or the app gets 42501.

Source: Supabase changelog and Securing your API.

Why the quick fix is the wrong fix

It breaks quietly, later

Nothing fails on Oct 30 itself. The failure arrives with your next migration, preview branch or fresh project, often from an AI builder that wrote the table for you.

GRANT ALL reopens everything

The copy-paste fix, grant all on all tables in schema public to anon, brings back the old exposure, including tables that never had RLS turned on.

Your code already knows

Which tables you read, insert, update or upsert is in your supabase.from() calls. Your policies say who may. This check combines the two into least-privilege grants.

      FAQ
      
  
      Does this upload my code or touch my database?
      No. Everything runs in your browser. Repo checks read public files from GitHub. The snapshot is a query you run yourself and paste back; this page never sees your database URL or keys. See the privacy note.
      
  
      How are the grants decided?
      For each table: the operations your client code performs (.select, .insert, .update, .upsert, .delete, plus tables embedded in select strings like prices(*)), limited to the roles your RLS policies allow. Policies TO public that depend on auth.uid() count for signed-in users only. Without app code, grants mirror the policies. service_role gets full access by default because server code and Edge Functions use it.
      
  
      My table has RLS off. Why no grants?
      Granting anon or authenticated on a table without RLS lets anyone with your public anon key read and change every row. The migration leaves those lines commented out until you enable RLS and add policies.
      
  
      What can't it see?
      Tables created in the Dashboard (use the snapshot), table names held in variables (.from(name)), raw fetch calls to /rest/v1, and SQL inside other tools. Server-side calls are recognised by the service-role key, admin client names or the supabase/functions folder.
      
  
      How is this different from the Supabase Security Advisor?
      The Advisor checks a live project. This check works on your migrations before you deploy, and writes the grants from your code. Use both.
      
  
      Is this affiliated with Supabase?
      No. It is an independent, open-source tool built from Supabase's and PostgreSQL's public documentation.
