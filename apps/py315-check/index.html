Python 3.15 is out, and "3.x" now means 3.15

Find the pinned dependencies that won't install on Python 3.15, and the smallest upgrade for each.

A dependency without a cp315 wheel makes pip compile it from source. In a slim Docker image or a fresh CI runner that means a long build or a failed one. Drop in your lockfile or a public repo to see exactly which of your versions are affected on Linux, macOS and Windows, plus the APIs 3.15 removed and the CI lines that already moved to 3.15.

Why now

  1. 9 Oct 2026 Python 3.15.0 released: UTF-8 by default, lazy imports, a batch of removed APIs
  2. Now Docker python:3, latest, slim and alpine point to 3.15.0, and actions/setup-python with '3.x' installs it
  3. 13 Oct 2026 90 of the 360 most-downloaded PyPI packages declare 3.15 support; older releases of the rest have no 3.15 wheels

Sources: What's new in 3.15, Docker official image tags, setup-python manifest, pyreadiness.org.

Why "works on 3.14" breaks on 3.15

Your pins are older than the fix

numpy only ships 3.15 wheels from 2.5.2, pandas from 3.0.6, psycopg2-binary from 2.9.13. A lockfile from last spring pins versions that predate 3.15, so pip falls back to a source build.

Readiness lists check "latest"

pyreadiness.org and package pages show whether the newest release supports 3.15. What matters is the version in your lockfile, on your platforms, and whether a parent package pins it exactly.

You may already be on 3.15

Floating tags like python:3-slim and python-version: '3.x' picked up 3.15 on their own. The first sign is often a failing build of a package you never touched.

      FAQ
      
  
      Does this upload my files?
      No. Files are read and analysed in your browser. With PyPI lookup on, your browser asks pypi.org for the public file list of each pinned package (names and versions only). Repo scans read public files from GitHub. See the privacy note.
      
  
      How is this different from pyreadiness.org?
      pyreadiness shows whether the latest release of the 360 most popular packages declares 3.15 support with a classifier. This check reads the versions you actually pin, looks at the real wheel files for your platforms (a package can work on 3.15 without the classifier, or declare it without Windows wheels), covers every package in your lockfile, and finds the smallest upgrade that fixes each.
      
  
      A package says "compiles from source". Will it fail?
      It depends on the package and your machine. pip needs a compiler, Python headers and the library's own build dependencies; slim and Alpine images have none of these. Even when it works, it can add minutes to every build. Upgrading to a release with a 3.15 wheel avoids the question.
      
  
      Why does it say to upgrade a different package?
      Some packages are pinned exactly by another one, for example pydantic pins pydantic-core. Upgrading the child alone would fail to resolve, so the check points you to the parent.
      
  
      Does it support conda?
      No. conda-forge builds its own packages and is still adding py315 builds. This check is for pip, uv, Poetry and Pipenv installs from PyPI.
      
  
      Is this affiliated with the Python Software Foundation?
      No. It is an independent, open-source tool built from the official Python documentation and PyPI's public APIs.
